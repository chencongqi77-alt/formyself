# 案例卡与图表取材清单

> 原则：案例不以“展示功能很多”为目标，而以“展示一条内容如何从数字资产保留证据地到达交互界面”为目标。

## 一、主案例的选择建议

### 案例 A：已发布的历史人物行迹（建议作为主案例）

**适合回答的问题**

- 已发布事件如何关联人物、地点、作品和来源；
- 读者如何从地图/时间顺序回到事件和作品；
- 发布前的来源、字段、关系和同步校验如何构成可信边界。

**取材步骤**

1. 从公开五表中选择一位材料较完整的诗人和两个至三个事件。
2. 为每个事件记录 personId、placeId、workIds、sourceRefs、reviewStatus。
3. 截取“选中地点/事件”的交互状态，并记录页面路径、筛选条件和截图日期。
4. 将一条 sourceRef 的精确定位写入案例表；正文不必复制原始长文本。

**可证明**

发布数据和交互视图之间的可追溯组织方式。

**不可证明**

该界面对学习效果的提升，或每个历史解释都已由独立学者逐条审定。

### 案例 B：诗中世界的地点候选（作为语义对照）

**适合回答的问题**

- 为什么“诗句提到地点”不等于“诗人到过地点”；
- 如何以 candidate-preview、区域注记和歧义不落点呈现不确定信息；
- 如何将大量候选转为可阅读的地点/作品界面。

**当前快照材料**

- 7,016 条原始候选；
- 5,450 条点图层关联；
- 896 条区域注解；
- 670 条严格门记录；
- 119 个地点展示实体。

这些数值是候选/筛选规模，不是精确率、事实数量或作者行迹数量。

### 案例 C：交游录的关系阅读（作为关系语义对照）

**适合回答的问题**

- 如何把大规模候选关系收缩为读者可浏览的焦点网络；
- 如何将关系桶、日期提示、信号数量和来源线索与交互焦点绑定；
- 为什么“阅读器可视边”不应被说成全量网络分析结果。

**当前快照材料**

- 27 位诗人的索引；
- 510 条直接边；
- 1,768 条关系阅读网络边；
- 其中多数前端载荷处于 candidate-preview 或 auto-accepted-preview 状态。

## 三、每张截图必须附带的元数据

截图不要只保留 PNG。应同时建立一个轻量 Markdown 或 CSV 清单，每张图至少记录：

| 字段 | 示例含义 |
| --- | --- |
| figureId | fig-03-journey-event |
| 页面路径 | journey、poem-world 或 social |
| 输入筛选 | 人物 ID、地点 ID、章节或关系筛选 |
| 数据状态 | published、candidate-preview 或其他原始字段值 |
| 数据锚点 | releaseId、manifest 路径或五表文件 SHA-256 |
| 来源锚点 | 所选对象的 sourceRef/locator，或明确写“候选线索” |
| 截图日期 | 生成日期 |
| 说明 | 该图要证明什么；不能证明什么 |

## 四、案例章节的最小写法

每个案例用同一小模板，便于后续 Agent 直接接力：

1. 研究对象与问题。
2. 上游资产及其状态。
3. 证据定位与语义判断。
4. 派生数据与交互状态。
5. 图中读者可以做什么。
6. 限制：候选性、空间近似、裁剪或尚未人工核验的部分。

这个模板足以支持一篇短论文的案例段落，不需要展开 React、地图瓦片或 API 调用细节。
