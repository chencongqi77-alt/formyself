## 二、隐私、版权与数据边界

- 不公开或附录化用户上传原文、私人摘录、提示词、模型响应、访问凭证或 API key。
- 用户上传即使可用于 private preview，也不能自动作为公开论文案例的证据；需先确认处理同意、保留期限和再利用授权。
- 对受版权保护书籍，只使用获得授权的短引用、书目、定位和原创摘要；不复制长篇扫描或转录文本。
- 不将已退役的 data/staging 候选、web/public/data 中的 preview，或旧文档中的构想混同为 records/published 事实。
- 不编辑 source-materials、CBDB、chinese-poetry、data/published 或 web/public/data 来“配合论文”；论文材料应是只读审计和新增文档。

## 三、文档时效与版本风险

部分早期文档与当前路由/数据载荷的状态可能不同。论文冻结前应优先以以下顺序判断状态：

1. 当前数据文件中的 reviewState、recordType、releaseId 和 manifest；
2. 当前校验命令输出；
3. schema 与脚本的实际约束；
4. 说明性文档。

当前目录不是 Git 工作树，因此不能以 commit 代替版本说明。请在论文或附录中使用检查日期、manifest 路径与 SHA-256、releaseId 以及命令输出作为复现锚点。

项目内的“2025 小论文汇编”粗转文件不应自动作为本研究数据、格式依据或引用来源：其内容和授权范围需另行确认。

## 四、后续写作 Agent 的起始问题

开始写大纲前，请先明确回答：

1. 目标读者/投稿场景是什么：学校项目论文、数字人文短文、教育技术报告，还是信息可视化案例？
2. 唯一核心贡献是什么：证据优先框架、可信私有处理，还是语义防错设计？
3. 主案例是否限定为 published 行迹数据？候选模块将以何种身份出现？
4. 论文是否要声称任何准确率、学习效果或用户体验改进？若要，现有或新增评价材料在哪里？
5. 哪些外部相关工作将支撑“来源溯源、历史不确定性、文学空间、交互可解释性”等概念？

如果其中任一问题没有答案，应先做选题决策或材料补证，不应直接扩写正文。

## 五、建议的后续工作顺序

1. 选定论文场景与唯一主张。
2. 冻结数据快照和图表清单。
3. 做最小来源抽样审计与候选误差分类。
4. 检索并筛选外部学术文献。
5. 先写“问题—框架—案例—限制”的详细大纲。
6. 最后才决定是否值得补用户研究或算法评价。

这样交接后，下一位 Agent 只需选择方向和补证计划，就能安全地开始论文写作，而不必重新猜测项目实际完成了什么。
