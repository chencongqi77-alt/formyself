# 从数字资产到交互式视据的处理流

> 目标：给论文方法部分提供一张可读、可审查的流程，而不展开脚本、接口或前端组件实现。

## 一、工作定义

本项目将地图、关系图、地点图和阅读卡视为**派生视图**。一项可以进入交互呈现的内容，至少需要回答四个问题：

1. 它来自哪个受治理的数字资产或数据快照？
2. 原文、记录或数据集中的证据定位在哪里？
3. 它是事实记录、候选，还是仅为展示/阅读辅助？
4. 它在什么 release、数据契约和交互语义下被呈现？

因此，交互不是“把数据画出来”的最后一步，而是把可追溯性、状态和语义约束带给读者的最后一层。

## 三、从资产到视图的五次转换

| 转换 | 产物 | 必须保留的信息 | 防止的错误 |
| --- | --- | --- | --- |
| 资产准入 | 来源快照、权限状态、SHA-256、接收回执 | 原始来源身份、版本、可见性 | 把来路不明或私有材料混入公开层 |
| 证据定位 | 页码、行号、JSON Pointer、文本 span 或记录 ID | 可回读的精确定位 | 用标题匹配或模型答案替代证据 |
| 候选与断言 | 人物、地点、时间、关系及其 confidence/review state | 原文名称、不确定性、产生 job | 把歧义解析成确定事实 |
| 审查与派生 | accepted/rejected/candidate、release manifest、文件哈希 | 决策人/策略、输入快照、版本 | 直接手改地图或网页 JSON |
| 交互呈现 | 地图点、事件、作品卡、边、场景节点 | sourceRefs、reviewState、模块语义 | 把不同含义的“地点/关系”混为同一种事实 |

## 四、三种视据的语义边界

| 视图 | 面向读者的交互 | 应表述为 | 不应表述为 |
| --- | --- | --- | --- |
| 行迹卷 | 选择人物、地点、事件或前后节点；联动时间、故事和作品 | 生平事件的叙事顺序 | 精确连续行旅轨迹，或所有时间均为精确公历 |
| 诗中世界 | 按人物筛选，点选地点或区域，查看关联诗作 | 作品文本所涉地点的候选/注记层 | 作者到访、作品创作地或可靠生平路线 |
| 交游录 | 搜索、筛选关系桶、缩放聚焦、点选边并查看来源线索 | 有证据线索支撑的关系阅读界面 | 全量社会网络，或自动确定的友敌判断 |

## 五、论文可用的简化用户流程

1. 读者从“行迹、诗中世界、社会关系”选择一个问题视角。
2. 读者筛选人物、地点或关系类型。
3. 地图/图形与右侧详情、作品或来源线索联动。
4. 读者回读相关文本、事件或来源定位，并看到该内容是 published、candidate-preview 还是其他状态。

论文应把第 4 步视为关键设计目标：交互视图的价值不在“图形更炫”，而在让读者能从聚合呈现返回到证据和状态。

## 六、适合放入方法部分的一段表述

本项目采用“事实优先、视图派生”的处理方式：数字资产首先被登记为具有版本、许可和精确定位的证据对象，随后形成带语义类别与审查状态的候选或断言；地图、关系图和阅读卡仅是这些记录在特定发布条件下的派生呈现。为避免空间与关系的过度推断，系统将生平路线、作品地点与人物关系明确分层，并要求不确定信息与候选状态随数据流保留至交互层。

这段只能用于描述框架和现有边界，不能暗示所有候选已完成学术审核或所有规划中的 release 流程已经实现。
